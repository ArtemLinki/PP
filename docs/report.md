## 1. Архитектура продукта

Разрабатываемый продукт — интернет-магазин электронных компонентов TechElectro. При проектировании было принято решение разделить систему на две независимые части — бэкенд и фронтенд — чтобы каждая могла развиваться отдельно и не мешала другой.

Бэкенд написан на NestJS и отвечает за всю бизнес-логику: работу с товарами, заказами, пользователями, корзиной, отзывами и ИИ-ассистентом. Данные хранятся в PostgreSQL, изображения — в отдельном хранилище MinIO, чтобы не засорять базу данных бинарными файлами. Для работы с базой используется Prisma — инструмент, который позволяет описывать структуру данных в одном файле и автоматически отслеживать её изменения через систему миграций.

Фронтенд реализован на Next.js. Этот фреймворк хорошо подходит для интернет-магазинов: страницы каталога отдаются быстро за счёт серверного рендеринга, что важно для поисковой оптимизации. Для UI-компонентов использована библиотека Mantine.

Всё окружение запускается через Docker Compose — одной командой поднимаются сразу база данных, хранилище файлов, бэкенд и фронтенд. Это упрощает развёртывание проекта на любой машине без ручной настройки.

Подобный подход является стандартным для коммерческих веб-приложений: он хорошо масштабируется, позволяет чётко разграничить ответственность между компонентами и упрощает сопровождение кода в дальнейшем.

## 2. Процесс разработки и тестирование

Проект разрабатывался итеративно — сначала была реализована рабочая основа (регистрация, каталог, корзина, заказы), после чего функционал постепенно расширялся, а обнаруживаемые ошибки исправлялись по мере выявления.

Все найденные проблемы фиксировались в отдельном документе в виде пронумерованного списка. Когда ошибка исправлялась — помечалась как решённая. Это позволяло не терять из виду накопившиеся задачи и видеть прогресс разработки.

Тестирование проводилось на двух уровнях. Во-первых, писались unit-тесты для сервисов бэкенда — проверялась бизнес-логика: правильно ли считается сумма заказа, корректно ли обрабатываются граничные случаи (например, попытка добавить в корзину больше товара, чем есть на складе). Во-вторых, после каждого значимого изменения вручную проверялись основные пользовательские сценарии в браузере: регистрация, добавление товара, оформление заказа, работа административной панели.

Основные ошибки, выявленные в ходе разработки:

Первое — браузер неправильно подставлял email в поле телефона при автозаполнении. Причиной оказалось отсутствие атрибута name у полей формы, из-за чего браузер самостоятельно пытался угадать назначение каждого поля.

Второе — удаление товара из административной панели завершалось ошибкой. Выяснилось, что в базе данных изначально не было настроено каскадное удаление: при попытке удалить товар система сообщала о нарушении ссылочной целостности. Потребовалось пересмотреть схему базы данных и прописать правила — что удалять вместе с товаром, а что оставлять.

Третье — статусы заказов в таблице визуально не обновлялись после изменения, хотя данные реально сохранялись. Проблема заключалась в том, что интерфейс «отменял» выбор пользователя до получения ответа от сервера. Решением стало оптимистичное обновление — интерфейс отображает изменение сразу, не ожидая подтверждения.

Четвёртое — при удалении последней фотографии товара она продолжала отображаться на карточке. Причина состояла в том, что при пустом списке изображений запрос на обновление просто не затрагивал это поле. Логика отправки данных была исправлена.

В целом большинство ошибок были связаны не со сложной логикой, а с недостаточно проработанными граничными случаями или пропущенными атрибутами.

## 3. Планирование и распределение задач

Проект разрабатывался в рамках небольшой команды. Планирование велось следующим образом: в начале был составлен список задач с расстановкой приоритетов — сначала то, без чего магазин не работает в принципе (авторизация, каталог, корзина), затем дополнительный функционал (отзывы, ИИ-ассистент, административная панель).

Каждое изменение оформлялось отдельным коммитом в Git с понятным описанием — что именно сделано и с какой целью. Это позволяло легко откатиться к любому состоянию, если что-то шло не так, а также давало чёткую историю изменений для всей команды.

Разработка прошла в два больших цикла: в первом был реализован основной функционал и закрыто большинство задач из беклога, во втором — устранялись более тонкие проблемы и добавлялись возможности, выявленные при детальном тестировании.

Задачи распределялись по компонентам системы: один разработчик преимущественно занимался бэкендом и базой данных, другой — фронтендом и пользовательским интерфейсом. При возникновении пересечений (например, при изменении типов данных, затрагивающих обе стороны) изменения согласовывались и вносились совместно.
